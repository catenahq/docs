Apps on a Catena server are published, protected, backed up, updated and monitored from labels written in the app's compose file. This page lists what an app needs, what each label does, and walks through Nextcloud as a complete example.

## Two ways to deploy

- **Catalog.** Portainer's **App Templates** list holds pre-wired apps. Each entry's details panel carries the setup notes. Labels, networks, placement and the sign-in client are already in place. Buttons in the panel's **Actions** tab, such as **Wire Nextcloud OIDC**, finish the wiring after the first deploy.
- **The app's own compose file**, deployed in Portainer (menu **Stacks**, then add a new one). Everything below applies to this path.

Apps run on Docker Swarm, so a compose file written for plain `docker compose` usually needs changes first (see [Swarm rules](#swarm-rules)). A catalog entry is always the shortest route when one exists for the software.

## Checklist

An app is fully managed when its compose file has:

1. The external network `catena-network`, with an alias on the public service.
2. `vps.route.host`, `vps.route.port` and `vps.route.service` on the public service.
3. `vps.auth.mode` and, for a private app, `vps.auth.groups`.
4. `deploy.restart_policy` on every service, and `node.labels.catena.role==data` on every service that mounts a volume.
5. No `depends_on`, no inline `configs:`, no short-form `tmpfs`, and published ports in long form with `mode: host`.
6. `vps.app` and `vps.component` on every service.
7. A full version tag on every image (`1.2.3`, not `latest`), plus `vps.auto-update` if the default is not wanted.
8. `vps.health.path` on a public app.
9. A dump-friendly database image, or a plan for the data an engine cannot dump automatically.

## Network and routing

The app joins the external network `catena-network` and gives the public service an alias on it. The reverse proxy reaches the app through that alias.

```yaml
services:
  web:
    image: example/web:1.2.3
    networks:
      catena-network:
        aliases:
          - my-app
      default: {}
    labels:
      - "vps.route.host=my-app.yourdomain.com"
      - "vps.route.port=8080"
      - "vps.route.service=web"

networks:
  catena-network:
    external: true
```

- `vps.route.host` is the public address. Without it the app is reachable only from inside the swarm and gets no Apps tile.
- `vps.route.port` is the port the app listens on inside the container (80 when omitted).
- `vps.route.service` names the compose service that receives the traffic. Its first `catena-network` alias is the backend address. When the service has no alias, the app's name in Portainer, lower-cased, is used.
- Internal services (database, cache) stay on the `default` network only, so they are unreachable from other apps and from the proxy.

The route appears within about 5 minutes. To apply it at once, open the panel's **Actions** tab and run **Sync all (apps + monitors)**.

## Access

Labels decide who reaches the app. A gate in front of the app (Keycloak sign-in) lets only the allowed groups through.

| Label | Effect |
|---|---|
| `vps.auth.mode` | `public`: no gate. `private`: signed-in members of the listed groups. `admin-only`: administrators only. |
| `vps.auth.groups` | Comma-separated Keycloak groups. A person in any one of them gets in (OR). Administrators are always allowed. The group `visitor` means public. |
| `vps.auth.protected` | `true` marks the app as one that must never be public: the panel warns when it resolves to public. |

Resolution rules:

- `private` with groups: those groups plus administrators.
- `private` without groups: `admin`, `client` and `staff`.
- Groups without a mode: those groups plus administrators.
- Nothing declared, or an unknown mode value: denied, so only administrators get in.
- `public` ignores `vps.auth.groups` (a warning is logged).

Groups must already exist in Keycloak: nothing creates them from a label. They are managed in the Keycloak admin console at `auth.yourdomain.com`, or in the **People** panel with Catena Pro (see [Sign-in and people](/en/configuration/sign-in-and-people/)).

These labels control who can reach the app, not what a person can do inside it. Roles and permissions inside the app are the app's own settings.

## Native OIDC login

An app that supports OpenID Connect can let people sign in with their Catena account instead of a separate password. Labels provision nothing here: the client is created by hand.

1. Open the Keycloak admin console at `auth.yourdomain.com`, realm `vps`, **Clients**, create a client.
2. Set a client ID, turn **Client authentication** on, and set the valid redirect URI to the app's callback address (the app's documentation names it).
3. Copy the client secret from the **Credentials** tab.
4. Pass the client ID, the secret and the issuer `https://auth.yourdomain.com/realms/vps` to the app through its environment, in the names the app expects.

The secret is entered as an environment variable in Portainer, never written into the compose file, so that it can be rotated without editing the file. Apps from the catalog already have their client.

`vps.auth.oidc`, `vps.auth.oidc.redirect_uris` and `vps.auth.oidc.scopes` only add an OIDC badge to the app's tile. They create no client.

See [Single sign-on](/en/features/single-sign-on/) for how sign-in works across apps.

## Swarm rules

A compose file is read by Docker Swarm, which refuses some keys outright and silently ignores others. The catalog is checked against these rules; a hand-written file has to follow them itself.

- **No `depends_on`.** Swarm has no start ordering and drops the key without a message. Give the dependent service a `deploy.restart_policy` so swarm retries it. When a crash and restart does damage (an installer that half-completes), make the entrypoint wait for the database itself.
- **`deploy.restart_policy.condition` on every service**, for example `any`.
- **Placement for volumes.** Any service that mounts a named volume or a host path carries `node.labels.catena.role==data`. A volume is local to a node: on another node swarm creates it empty, without an error.
- **Published ports** use the long form with `mode: host`, and each port is declared with `vps.expose.tcp` or `vps.expose.udp`. Host mode keeps the real client address; the default mesh replaces it.
- **No inline `configs:`.** A `file:` or `content:` entry cannot be resolved when Portainer deploys the file. Write the config file from the service's entrypoint instead. Only `external: true` configs are accepted.
- **`tmpfs` in long form** (`type: tmpfs`). The short key is dropped silently. A tmpfs mount is `noexec`; a path that needs execution has to be a volume.
- **Refused keys**, which make swarm reject the whole file: `mem_limit`, `memswap_limit`, `cpus`, `cpu_shares`, `volumes_from`, `profiles`, `scale`. Limits go in `deploy.resources.limits`; the replica count goes in `deploy.replicas`.
- **Dropped keys** with no effect: `restart`, `container_name`, `expose`, `links`, `external_links`, `build`, `network_mode`, `pid`, `privileged`, `security_opt`, `devices`, `shm_size`. Images are built and published elsewhere; swarm only pulls them.

```yaml
services:
  relay:
    image: example/relay:1.2.3
    deploy:
      restart_policy:
        condition: any
    ports:
      - target: 3478
        published: 3478
        protocol: udp
        mode: host
    labels:
      - "vps.expose.udp=3478"
```

## Storage and backups

- **Named volumes** live under the Docker volumes folder and are included in every backup. Declare each volume explicitly: anonymous volumes are backed up too, but a single-app restore cannot reach them.
- **Bind mounts** inside the apps area are included. A bind mount to any other absolute path makes the backup fail, unless that folder is listed under **Settings** > **Backup repository** > **Other folders to back up (separated by commas)**. See [Backups and S3 storage](/en/configuration/backups/).
- **Databases are dumped automatically** before each backup:
  - a running container whose image name contains `postgres` is dumped with `pg_dumpall`, using the user in `POSTGRES_USER`;
  - a container whose image name contains `mariadb` or `mysql` is dumped, and needs `MARIADB_ROOT_PASSWORD` or `MYSQL_ROOT_PASSWORD` in its environment.
  - A dump that fails fails the backup. No label controls this: the image name decides.
- **Other engines** (MongoDB, SQLite and similar) get no automatic dump. The app needs its own export, or a volume copy that is consistent on its own.
- **Large file sets** belong in S3-backed storage rather than in a local volume, which keeps the backup small. The Nextcloud template stores files in a bucket, and only the application data stays on a local volume.

A backup does not pause the app: nothing is put in maintenance mode around the snapshot.

## Identity labels

`vps.app` and `vps.component` tell Catena which containers belong to which app and what each one does.

| Label | Value | Used for |
|---|---|---|
| `vps.app` | One name shared by every service of the app, such as `my-app` | Restore membership, single-app restore, update and restore lookup. Survives a rename in Portainer. |
| `vps.component` | The service name, such as `web`, `db`, `redis` | Recognizing the database tier so it is never paused, and matching a service to its dump. |

Both should be set on every service. Deploying the app in Portainer under a name equal to `vps.app` keeps volume names (`<app>_<volume>`) aligned with the single-app restore.

## Updates

Only images with a full version tag are updated automatically:

| Tag form | Example | Managed |
|---|---|---|
| Full version | `1.2.3`, `v1.2.3`, `1.2.3-alpine`, `1.2.3-apache` | Yes |
| Partial version | `1.2`, `1` | No |
| Floating | `latest`, `stable`, `alpine`, `edge`, `main` | No |

`vps.auto-update` sets how far a version may move:

| Value | Allowed |
|---|---|
| `patch` (default) | `1.2.3` to `1.2.4` |
| `minor` | `1.2.3` to `1.3.0` |
| `major` | `1.2.3` to `2.0.0` |
| `off` | Never |

A missing or invalid value counts as `patch`. A tag that is not a full version is never changed, whatever the label says. Services that share one image take the most restrictive label. The updates themselves run in the nightly maintenance, which needs Catena Pro or Catena Business ([editions](https://catena.run/en/#pricing)); see [Updates](/en/configuration/updates/).

## Monitoring and dashboard

| Label | Effect |
|---|---|
| `vps.health.path` | Path probed by the status page, for example `/health`. The probe expects a 200 reply. |
| `vps.health.expect` | Text that must appear in the reply body. |
| `vps.display-name` | Title of the app's card on the status page. |
| `vps.homepage.name` | Tile title on the **Apps** tab. Defaults to the app's name in Portainer. |
| `vps.homepage.icon` | Tile icon, such as `mdi-application` (the default). |
| `vps.homepage.description` | Tile subtitle. |
| `vps.homepage.hidden` | `true` hides the tile from everyone except administrators. |

Without `vps.health.path`, the probe requests the address and expects the sign-in redirect. A public app has no such redirect, so its card shows red. Set `vps.health.path` on every public app.

Tiles on the **Apps** tab render live from Portainer and need a `vps.route.host`. The status-page sync runs about every 10 minutes, or on **Sync all (apps + monitors)** in **Actions**. See [Monitoring and alerts](/en/features/monitoring-alerts/).

## Label reference

| Label | Values | Default | Effect |
|---|---|---|---|
| `vps.route.host` | Address under `yourdomain.com` | none (no route) | Publishes the app |
| `vps.route.port` | Port number | 80 | Container port behind the route |
| `vps.route.service` | Compose service name | the Portainer app name, lower-cased | Service that receives traffic |
| `vps.auth.mode` | `public`, `private`, `admin-only` | none (denied) | Gate in front of the app |
| `vps.auth.groups` | Comma-separated groups | none | Groups allowed in (OR), plus administrators |
| `vps.auth.protected` | `true`, `false` | `false` | Warns when the app resolves to public |
| `vps.auth.oidc` | `true`, `false` | `false` | OIDC badge on the tile only |
| `vps.auth.oidc.redirect_uris` | Comma-separated addresses | none | Tile badge data only |
| `vps.auth.oidc.scopes` | Space-separated scopes | none | Tile badge data only |
| `vps.app` | Name | none | App identity for restore and updates |
| `vps.component` | Service name | none | Role of the service (database tier detection) |
| `vps.auto-update` | `off`, `patch`, `minor`, `major` | `patch` | Allowed version movement |
| `vps.health.path` | URL path | none | Status-page probe path |
| `vps.health.expect` | Text | none | Required text in the reply |
| `vps.display-name` | Text | the app name | Status-page card title |
| `vps.homepage.name` | Text | the app name | Tile title |
| `vps.homepage.icon` | Icon name | `mdi-application` | Tile icon |
| `vps.homepage.description` | Text | none | Tile subtitle |
| `vps.homepage.hidden` | `true`, `false` | `false` | Hides the tile from non-administrators |
| `vps.expose.tcp` | Ports or ranges (`25,465`, `7000-7010`) | none | Opens published TCP ports |
| `vps.expose.udp` | Ports or ranges | none | Opens published UDP ports |

Labels may be written as a list (`"key=value"`) or as a map. A `${VARIABLE}` in a value is replaced with the app's environment variable before the label is read.

### Why each part is there

- **Storage.** User files go to an S3 bucket through the `OBJECTSTORE_S3_*` variables. The backup then holds only the database and the small local volumes, and the bucket is covered by its own provider-side durability. `nc-data` still holds logs and application data, so it is a named volume. `nc-html` holds the code tree: with it persisted, a recreated container is recognized as an existing install and upgraded, instead of being installed again over live data.
- **Placement.** `app`, `db` and `cron` mount volumes, so all three are pinned to the data node. `redis` keeps nothing and needs no pin: a missing cache is a cache miss.
- **Database wait instead of `depends_on`.** Swarm drops `depends_on`. A crash-and-restart loop until the database answers is not safe for Nextcloud either: the installer gives up after ten tries, but by then the version file is already written, so the next start takes the upgrade path and the instance stays "not installed" until the volume is wiped. The entrypoint therefore opens a real database connection (not just a TCP check, because Postgres accepts connections while still starting) and only then hands over to the image's own entrypoint. After 300 seconds it exits so swarm restarts the task.
- **Hook for configuration.** The image fills its config folder only when that folder is empty, so a config file written before startup breaks the first run. The entrypoint writes a `before-starting` hook that the image runs after populating the folder. `$$` is compose's escape for a literal `$`.
- **Cron service.** The same image runs `/cron.sh` for background jobs. It shares the four volumes with `app`, so it lands on the same node and waits for the database in the same way.
- **Trusted domains and proxy.** TLS ends at the edge. `OVERWRITEPROTOCOL=https`, `OVERWRITEHOST` and `OVERWRITECLIURL` make Nextcloud write https addresses, `TRUSTED_PROXIES` covers the private ranges that Catena's proxy uses, and `NEXTCLOUD_TRUSTED_DOMAINS` is the public hostname.
- **Chunk size.** Cloudflare caps a request body at 100 MB on its Free and Pro plans. Nextcloud's default upload chunk is 100 MiB, which fails at the edge and is retried without end. 80 MiB (`83886080`) leaves headroom. Setting it to 0 disables chunking and breaks every upload over 100 MB.
- **Access.** `vps.auth.mode=public` leaves Nextcloud's own login in charge, which keeps anonymous share links (`/s/...`) working for people with no account. Sign-in through Keycloak is added inside the app (below).
- **Health.** `vps.health.path=/status.php` keeps the status card green; a public app without it is probed for a redirect it never gives.
- **Backups.** The `db` service image contains `postgres` and has `POSTGRES_USER` set, so it is dumped before each backup.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| 502 or 503 on the address | The proxy cannot reach the app. Check that the public service is on `catena-network`, that its alias exists, that `vps.route.service` names the right service and `vps.route.port` matches the listening port. Logs are in Portainer. |
| 403 after signing in | The person is in none of the allowed groups. Check `vps.auth.groups` and the group membership in **People** or Keycloak. The group name must exist and match exactly. |
| Only administrators get in | No `vps.auth.mode` or groups are declared (default is deny), or the mode value is not one of `public`, `private`, `admin-only`. |
| No route after a deploy | The sync runs every 5 minutes. Run **Sync all (apps + monitors)** in **Actions**. A host with no `vps.route.host` is never routed. |
| Red card on the status page | A public app with no `vps.health.path`, or a path that does not answer 200, or a `vps.health.expect` text that is absent from the reply. |
| Backup failed on a bind mount | The mount is outside the apps area. Move the data to a named volume, or list the folder under **Settings** > **Backup repository** > **Other folders to back up (separated by commas)**. |
| Backup failed on a database | The dump failed. A MariaDB or MySQL container needs `MARIADB_ROOT_PASSWORD` or `MYSQL_ROOT_PASSWORD`; a Postgres container needs a valid `POSTGRES_USER`. |
| Update skipped | The tag is not a full version (`latest`, `1.2`), `vps.auto-update` is `off`, or the move exceeds the label (a major bump under `patch`). The newest version may also be held by the vulnerability or waiting-period checks. |
| Service restarts in a loop at first deploy | No wait for the database. Add one in the entrypoint. |
| Data missing after a node change | A service with a volume lacked `node.labels.catena.role==data` and started on another node with an empty volume. |
