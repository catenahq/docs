Catena manages an app from labels written in its compose file: it publishes the address, puts the sign-in gate in front, backs up the data, updates the images and watches the app on the status page. In this guide, you prepare an app's own compose file and deploy it from Portainer. An app that goes through every step is fully managed.

When the software is in the catalog (Portainer, **App Templates**), the catalog entry is the shorter route: its labels, networks, placement and sign-in client are already in place, and the buttons in the panel's **Actions** tab finish the wiring after the first deploy.

## How Catena reads an app

An app is a set of services. One of them, the **front-door service**, answers the web requests: the web server or the application server. The others (database, cache, background workers) are internal and stay out of reach of the internet and of other apps.

You write labels under each service's own `labels:` key, as a list with one `"key=value"` per line. The status page, restores, migrations and updates read them from there; labels under `deploy.labels` are not seen by them.

A service that carries `vps.route.host` has a public **address**, and its port, who gets in and health check are read from that service alone. Most apps have one address, on the front-door service. An app can have several, such as a public site and an admin page served by another service. With two or more, you mark the **main address** with `vps.route.main=true` on its service. The labels that describe the app as a whole (its tile, its title on the status page, its sign-in entry, `vps.auth.protected`) are read from the main address's service only, as the running app has them, and are ignored on any other service. With one address, that service is the main address and needs no mark. When an app has two or more addresses and none or several are marked main, the app gets no route.

Access is set per address and is never inherited: an address with no access label admits administrators only, even when the main address is public. Two addresses cannot share a host name: the one deployed first keeps it, and the other gets no route. The update policy and the published ports describe a single service, and each is optional. Which app a service belongs to is the app's name in Portainer, and the service is its key in the file; Catena reads both from Docker Swarm itself, so no label names them. The [label reference](#label-reference) says where each label goes.

A label value can be a `${VARIABLE}` from Portainer's environment variables: Catena reads the value the deployed service received. A `vps.*` label that Catena does not recognise has no effect.

## Step 1: Choose the app's name

Give the app one short name made of lower-case letters, digits and hyphens, such as `my-app`. It is the app's name in Portainer, which you give at deploy time (step 7). Restores, migrations and updates find the app by that name, and the proxy reaches the front-door service at `my-app_web`: the app's name, an underscore and the service's key in the file.

## Step 2: Make the file ready for Docker Swarm

Apps run on Docker Swarm, which refuses some compose keys outright and silently ignores others. The catalog is checked against these rules; when you write a file by hand, you follow them yourself.

- **Restart policy.** Swarm restarts a stopped service by default. Write `deploy.restart_policy` only for a service that must not restart (`condition: none`) or only after a failure (`condition: on-failure`), such as a setup job.
- **Placement for data.** Every service that mounts a named volume or a host folder has the placement constraint `node.labels.catena.role==data`. A volume is local to one server: on another, swarm creates it empty, without an error.
- **No `depends_on`.** Swarm has no start ordering and drops the key without a message. Swarm restarts a service that started too early. When a crash and restart does damage (an installer that half-completes), the entrypoint waits for the database itself.
- **No inline `configs:`.** A `file:` or `content:` entry cannot be resolved when Portainer deploys the file. The service's entrypoint writes the config file instead. Only `external: true` configs are accepted.
- **`tmpfs` in long form** (`type: tmpfs`). The short key is dropped silently. A tmpfs mount is `noexec`; a path that needs execution is a volume.
- **Published ports in long form** with `mode: host`, which keeps the real client address (the default mode replaces it). See [step 4](#step-4-label-the-front-door) for the label that opens them in the firewall.
- **Refused keys**, which make swarm reject the whole file: `mem_limit`, `memswap_limit`, `cpus`, `cpu_shares`, `volumes_from`, `profiles`, `scale`. Limits go in `deploy.resources.limits`, the replica count in `deploy.replicas`.
- **Dropped keys**, with no effect: `restart`, `container_name`, `expose`, `links`, `external_links`, `build`, `network_mode`, `pid`, `privileged`, `security_opt`, `devices`, `shm_size`. Images are built and published elsewhere; swarm only pulls them.
- **Full version tags.** Every image carries a full version tag, such as `1.2.3` or `1.2.3-alpine`. Only those are updated automatically: `latest`, `stable`, `1.2` or `1` are never touched.

## Step 3: Connect the front door

The front-door service joins the external network `catena-network` and keeps the app's own `default` network to reach the internal services. No alias is needed. The internal services stay on `default` only. The file declares `catena-network` as `external: true` (see the skeleton above).

The reverse proxy reaches the front-door service through that network, and every other service with an address the same way. A service with an address that is not on `catena-network` gets no route for that address. An internal service with no `catena-network` entry is unreachable from the proxy and from other apps.

## Step 4: Label the front door

Write these labels on the front-door service:

1. `vps.route.host` with the public address, such as `my-app.yourdomain.com`. Without it the app has no route, no tile and no status-page card.
2. `vps.route.port` with the port the app listens on inside its container, when it is not 80.
3. Who gets in:
   - `vps.auth.mode=public` for an app open to everyone. The app's own login, if it has one, stays in charge.
   - `vps.auth.groups` with the Keycloak groups allowed in, for a private app. A person in any one of them gets in.
   - Neither label: only administrators get in.
4. `vps.health.path` with an address of the app that answers 200 when the app works, such as `/health`. Without it, the status page checks the app's front page: a public app is up when the page answers without an error, and an app behind sign-in when it sends visitors to sign in.
5. Optionally, the tile's name, icon and description on the **Apps** tab, and the title of the status-page card.

Administrators always get in. Groups are not created by a label: they already exist in Keycloak, managed in its admin console at `auth.yourdomain.com` or in the **People** panel with Catena Pro (see [Sign-in and people](/en/configuration/sign-in-and-people/)). The gate decides who reaches the app, not what a person can do inside it: roles and permissions inside the app are the app's own settings.

### Another address (optional)

When another service of the app answers on an address of its own, such as an admin page, give that service its labels too:

1. On the front-door service, add `vps.route.main=true`. It marks the address that the tile opens and that carries the app-wide labels.
2. On the other service, add `vps.route.host` with its own address, `vps.route.port` when it is not 80, and its access: `vps.auth.mode=public`, or `vps.auth.groups` with the groups allowed in. With neither, only administrators get in, whatever the main address allows.
3. Add `vps.health.path` on it when its front page is not a good check. The status page then shows one card for each address.
4. Join that service to `catena-network` too (step 3).

## Step 5: Set the update policy (optional)

By default an image moves to newer patch releases only. A service that should move further, or not at all, carries `vps.auto-update` (see [Updates](#updates)).

Nothing else is labelled per service. A service whose image is a database or cache (PostgreSQL, PostGIS, TimescaleDB, MariaDB, MySQL, MongoDB, Redis, Valkey, KeyDB, Memcached, Elasticsearch, OpenSearch) is recognised from its image and keeps running when a migration pauses the rest of the app.

## Step 6: Plan the data

- **Named volumes** live in the Docker volumes folder and are in every backup. Each volume is declared by name: anonymous volumes are backed up too, but a single-app restore cannot reach them.
- **Bind mounts** inside the apps area are included. A bind mount to any other absolute path makes the backup fail, unless you list that folder under **Settings** > **Backup repository** > **Other folders to back up (separated by commas)**. See [Backups and S3 storage](/en/configuration/backups/).
- **Databases are dumped automatically** before each backup. The image name decides, not a label:
  - a running container whose image name contains `postgres` is dumped with `pg_dumpall`, as the user in `POSTGRES_USER`;
  - a container whose image name contains `mariadb` or `mysql` is dumped, and needs `MARIADB_ROOT_PASSWORD` or `MYSQL_ROOT_PASSWORD` in its environment;
  - a dump that fails fails the backup.
- **Other engines** (MongoDB, SQLite and similar) get no automatic dump. You need the app's own export, or a volume copy that is consistent on its own.
- **Large file sets** belong in S3-backed storage rather than in a local volume, which keeps the backup small.

A backup does not pause an app added by hand: nothing is put in maintenance mode around the snapshot. A catalog entry can ask for it instead: Nextcloud, for one, is put in maintenance mode while the nightly maintenance takes its backup, and taken out of it afterwards, even when the backup fails.

## Step 7: Deploy

1. In Portainer, open **Stacks** and add a new one.
2. Set its name to the app's name from step 1.
3. Paste the compose file in the web editor.
4. Enter passwords and keys in the **Environment variables** section and refer to them in the file as `${VARIABLE}`. They stay out of the file, so you can rotate them without editing it.
5. Deploy.

## Step 8: Check

1. Wait a few seconds: Catena picks up the deploy by itself. To run it at once, open the panel's **Actions** tab and run **Sync all (apps + monitors)**.
2. Open the address. A private app shows the sign-in page first; a public app opens directly.
3. The app's tile is on the **Apps** tab, and its card on the status page turns green.

When a check fails, the [troubleshooting table](#troubleshooting) lists the usual causes.

## Sign in with Catena accounts (optional)

An app that supports OpenID Connect can let people sign in with their Catena account instead of a separate password. Labels make Catena create the app's own sign-in entry in Keycloak and hand the app its id, secret and issuer.

1. Add these labels to the front-door service:
   - `vps.auth.oidc=true`.
   - `vps.auth.oidc.redirect_uris` with the app's callback address (the app's documentation names it), such as `https://my-app.yourdomain.com/auth/callback`. Separate several addresses with commas.
   - `vps.auth.oidc.public=true` only for an app that cannot keep a secret, such as a phone app. The entry then has no secret and requires PKCE.
2. In the compose file, pass the three values to the app under the names it expects, with an empty default so that the first deploy works: `${OIDC_CLIENT_ID:-}`, `${OIDC_CLIENT_SECRET:-}` (absent for a public app) and `${OIDC_ISSUER_URL:-}`.
3. Deploy the app, then run **Sync all (apps + monitors)** in the **Actions** tab. Catena creates the entry, writes the three values into the app's environment in Portainer and redeploys the app when they change. Keycloak generates the secret; Catena copies it.

Each return address is `https://` on a domain this server serves, or a phone app's own scheme such as `app.immich:///oauth-callback`. A `*`, plain `http://` or a `#` is refused. When a label is wrong, Catena makes and changes nothing for that app.

Who can sign in through the app's own button follows the app's groups: only administrators for an app only they can open, staff and administrators when the groups go beyond `admin`, and every account when `client` is among them. A public app with no `vps.auth.groups` admits staff and administrators.

Catena only changes entries it made. An entry with the same name that you made by hand is never taken over. Removing the labels, or the app, deletes the entry Catena made.

To check that it worked:

- On the **Apps** tab, an administrator sees on the app's tile **sign-in ready**, **sign-in waiting** or **sign-in failed**, with the reason, in place of the OIDC badge. Staff see the OIDC badge.
- Waiting means Catena tries again on its own. Failed means something needs fixing, and the tile says what. The **Log** tab also names the app and the reason.

See [Single sign-on](/en/features/single-sign-on/) for how sign-in works across apps.

## Label reference

Every label goes under the service's own `labels:` key.

### On each service with an address

On every service that carries `vps.route.host`: the front-door service and any other address. Each address reads its own.

| Label | Values | Default | Description |
|---|---|---|---|
| `vps.route.host` | An address under `yourdomain.com` | none | Public address. The service that carries it has an address of the app. Without it on any service, the app has no route, no tile and no status-page card. Two addresses cannot share a host name: the one deployed first keeps it. |
| `vps.route.port` | A port number | `80` | Port the service listens on inside its container. |
| `vps.auth.mode` | `public`, `private`, `admin-only` | none | `public`: no gate. `private`: the groups in `vps.auth.groups`, or `admin`, `client` and `staff` when none are listed. `admin-only`: administrators only. |
| `vps.auth.groups` | Keycloak group names, comma-separated | none | Groups allowed in; a person in any one of them gets in. Ignored with `public` and `admin-only`. The group `visitor` makes the address public. |
| `vps.health.path` | A URL path | none | Address the status page checks every 2 minutes; the address is up when it answers 200. Without it, the check reads the front page: a public address is up when it answers without an error, an address behind sign-in when it sends visitors to sign in. |
| `vps.health.expect` | Text | none | Text the reply must contain. Used only with `vps.health.path`. |

With neither `vps.auth.mode` nor `vps.auth.groups`, only administrators get in. This holds for each address on its own: an address does not take the access of the main address. Administrators always get into a private address.

### On the front-door service, once

On the main address's service only. On any other service these labels are ignored.

| Label | Values | Default | Description |
|---|---|---|---|
| `vps.route.main` | `true`, `false` | `false` | Marks the main address. Needed only when the app has two or more addresses, on exactly one service. With none or several marked, the app has no route. |
| `vps.auth.protected` | `true`, `false` | `false` | `true` marks an app that must not be public: when its labels make it public anyway, its tile on **Apps** carries the badge "should require sign-in", shown to administrators only. |
| `vps.auth.oidc` | `true`, `false` | `false` | Catena creates the app's own sign-in entry in Keycloak and puts `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` and `OIDC_ISSUER_URL` in the app's environment. Staff see an OIDC badge on the tile; administrators see the state of the sign-in. |
| `vps.auth.oidc.redirect_uris` | Addresses, comma-separated | none | Return addresses of the sign-in entry. Required with `vps.auth.oidc`. See [Sign in with Catena accounts](#sign-in-with-catena-accounts-optional). |
| `vps.auth.oidc.public` | `true`, `false` | `false` | `true` for an app that sends no secret: the entry has no secret and requires PKCE. |
| `vps.display-name` | Text | the main address | Title of the main address's card on the status page. The other addresses' cards are titled by their address. |
| `vps.homepage.name` | Text | the app's name in Portainer | Title of the tile on the **Apps** tab. |
| `vps.homepage.icon` | An icon name, or an image address | `mdi-application` | Tile icon. An address starting with `http` is shown as an image. |
| `vps.homepage.description` | Text | none | Tile subtitle. |
| `vps.homepage.hidden` | `true`, `false` | `false` | Hides the tile from everyone except administrators. The app stays reachable. |

### Updates

On any service, optional, and read from whichever service carries it.

| Label | Values | Default | Description |
|---|---|---|---|
| `vps.auto-update` | `off`, `patch`, `minor`, `patch+minor`, `major` | `patch` | How far the image's version may move. `patch` keeps the major and minor numbers (`1.2.3` to `1.2.9`). `minor` and `patch+minor` keep the major number (`1.2.3` to `1.9.0`). `major` takes any newer release (`1.2.3` to `2.0.0`). `off` never moves it. An invalid value counts as `patch`. |

Only images with a full version tag are updated. Services that run the same image move together, under the most restrictive of their labels; a service without the label counts as `patch`. The updates run in the nightly maintenance, which needs Catena Pro or Catena Business ([editions](https://catena.run/en/#pricing)); see [Updates](/en/configuration/updates/).

### Published ports

On the service that publishes the ports.

| Label | Values | Default | Description |
|---|---|---|---|
| `vps.expose.tcp` | Ports or ranges, comma-separated (`25,465`, `7000-7010`) | none | Opens these TCP ports to the internet in the server's firewall. The service publishes them itself, in long form with `mode: host`. An invalid entry is ignored. |
| `vps.expose.udp` | Ports or ranges, comma-separated | none | The same for UDP ports. |

### Why each part is there

- **Storage.** User files go to an S3 bucket through the `OBJECTSTORE_S3_*` variables. The backup then holds only the database and the small local volumes, and the bucket is covered by its own provider-side durability. `nc-data` still holds logs and application data, so it is a named volume. `nc-html` holds the code tree: with it persisted, a recreated container is recognized as an existing install and upgraded, instead of being installed again over live data.
- **Placement.** `app`, `db` and `cron` mount volumes, so all three are pinned to the data node. `redis` keeps nothing and needs no pin: a missing cache is a cache miss.
- **Database wait instead of `depends_on`.** A crash-and-restart loop until the database answers is not safe for Nextcloud: the installer gives up after ten tries, but by then the version file is already written, so the next start takes the upgrade path and the instance stays "not installed" until the volume is wiped. The entrypoint therefore opens a real database connection (not just a TCP check, because Postgres accepts connections while still starting) and only then hands over to the image's own entrypoint. After 300 seconds it exits so swarm restarts the task.
- **Hook for configuration.** The image fills its config folder only when that folder is empty, so a config file written before startup breaks the first run. The entrypoint writes a `before-starting` hook that the image runs after populating the folder. `$$` is compose's escape for a literal `$`.
- **Cron service.** The same image runs `/cron.sh` for background jobs. It shares the four volumes with `app`, so it lands on the same node and waits for the database in the same way.
- **Trusted domains and proxy.** TLS ends at the edge. `OVERWRITEPROTOCOL=https`, `OVERWRITEHOST` and `OVERWRITECLIURL` make Nextcloud write https addresses, `TRUSTED_PROXIES` covers the private ranges that Catena's proxy uses, and `NEXTCLOUD_TRUSTED_DOMAINS` is the public hostname.
- **Chunk size.** Cloudflare caps a request body at 100 MB on its Free and Pro plans. Nextcloud's default upload chunk is 100 MiB, which fails at the edge and is retried without end. 80 MiB (`83886080`) leaves headroom. Setting it to 0 disables chunking and breaks every upload over 100 MB.
- **Access.** `vps.auth.mode=public` leaves Nextcloud's own login in charge, which keeps anonymous share links (`/s/...`) working for people with no account. Sign-in through Keycloak is added inside the app (below).
- **Health.** `vps.health.path=/status.php` checks the page that says Nextcloud itself is up, beyond its front page.
- **Backups.** The `db` service image contains `postgres` and has `POSTGRES_USER` set, so it is dumped before each backup.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| 502 or 503 on the address | The proxy cannot reach the app. The front-door service is on `catena-network`, and `vps.route.port` is the port it listens on. Read the logs in Portainer. |
| 403 after signing in | The person is in none of the allowed groups. The group in `vps.auth.groups` exists in Keycloak, matches exactly (letter case included), and the person is a member (**People** or Keycloak). |
| Only administrators get in | Neither `vps.auth.mode` nor `vps.auth.groups` is set, or the mode is not `public`, `private` or `admin-only` and no groups are listed. |
| No route, or the wrong address or access | No `vps.route.host`, several addresses with none or two marked `vps.route.main=true`, or a front-door service that is not on `catena-network`. An app-wide label on a service other than the main address's is ignored. The route sync runs seconds after a deploy and every hour; **Sync all (apps + monitors)** in **Actions** runs it at once. |
| One address does not answer | Another address on this server already uses its host name, or its service is not on `catena-network`. The tile tells an administrator which address and why. Give the address a host name of its own, or join its service to `catena-network`, then deploy again. |
| Red card on the status page | A public app whose front page answers an error, an app behind sign-in that does not send visitors to sign in, a `vps.health.path` that does not answer 200, or a `vps.health.expect` text that is absent from the reply. |
| The tile says **sign-in failed** or **sign-in waiting** | Read the reason on the tile. A return address in `vps.auth.oidc.redirect_uris` must be `https://` on a domain this server serves, with no `*` and no `#`. Fix the label, deploy the app again and run **Sync all (apps + monitors)**. |
| Backup failed on a bind mount | The mount is outside the apps area. Move the data to a named volume, or list the folder under **Settings** > **Backup repository** > **Other folders to back up (separated by commas)**. |
| Backup failed on a database | The dump failed. A MariaDB or MySQL container needs `MARIADB_ROOT_PASSWORD` or `MYSQL_ROOT_PASSWORD`; a Postgres container needs a valid `POSTGRES_USER`. |
| Update skipped | The tag is not a full version (`latest`, `1.2`), `vps.auto-update` is `off`, or the move exceeds the label (a major release under `patch`). The newest release may also be held back by the vulnerability or waiting-period checks. |
| Service restarts in a loop at first deploy | Nothing waits for the database. The service's entrypoint waits for it, as in the Nextcloud example. |
| Data missing after a node change | A service with a volume lacked `node.labels.catena.role==data` and started on another node with an empty volume. |
